# Atomic mapped deletion lifecycle

A stale `_replace_by` group previously reached `ConsumableRepository::replaceGroup` only after group membership and audit cleanup. Both PostgreSQL and MariaDB then refused the recipient foreign key while the source group survived with its membership and history already removed. The public mapped delete/purge operation now validates and locks its source and replacement before purge hooks, and runs the existing lifecycle on the supplied writer connection inside one DBAL transaction or savepoint. Invalid targets return false without starting cleanup; exceptions remain visible after database rollback.

`DeletionRepository` resolves the model's actual public index through ORM metadata, including association indexes such as `TicketSatisfaction::tickets_id`, and separately retains the canonical record identity. Self/descendant replacements are rejected through the declared owning parent association rather than cached names or descendants. Same-entity replacements and recursive ancestors retain the confirmation selector's behavior; property-declared global scope remains available. User is global and its preferred entity does not become ownership. This backend boundary preserves existing source authorization in forms/API and existing backend/cron callers; it does not introduce blanket session permissions. Read-connection deletion remains refused. Absent, NULL and zero replacements remain with the owning property's existing lifecycle policy.

Hook ordering, public child updates/deletes, notifications, audit history, tree reparenting and purge cleanup stay in the application models. Hook-rewritten replacements are checked again before cleanup. The locked canonical identity, public association index and supplied source identity remain fixed after plugin/model pre-delete hooks; a hook cannot redirect an authorized purge to an unlocked record or rewrite the protected root identity. Refused nested purges cancel the surrounding unit even when a caller discards the boolean; cleanup callers also propagate refused related updates. Explicit cancellation and exceptions restore the source model's ordinary lifecycle state and session state, remove uncommitted success messages and retain explicit failure feedback. Tree reads during the unit use the writer database and invalidate touched external keys instead of publishing an uncommitted hierarchy; database-derived caches participate in rollback.

User's historical partial deletion is a distinct successful domain operation: when the actor has access to only some grants, the account remains, accessible grants detach atomically, and the public `delete()` result remains false. `DeletionDecision::ScopedDetachment` distinguishes that committed outcome from cancellation; a successful nested detachment does not cancel an independent parent operation. Decisions query current writer-side grants, including when one User model is reused for another account. Legacy `pre_deleteItem` overrides still execute and their false is cancellation, including overrides calling the parent before cancelling. Extensions that intentionally require scoped detachment must override the structured `deletionDecision()` API (the protected `decideAccountDeletion()` provides User's default decision). No hidden mutable status flag converts an extension's cancellation into a commit.

Queued notification generation stays inside the lifecycle. Central `QueuedNotification::forceSendFor` defers delivery during database transactions, covering nested add/update/delete/restore and User-specific force-send callers. A guard-owned physical commit can deliver the deduplicated pending set afterward. A savepoint release in a caller-owned transaction leaves pending queue rows for normal cron/delivery; it does not send before the caller commits. Caller rollback therefore removes the uncommitted queue without external delivery. Delivery errors after physical commit do not restore a model that was actually deleted.

Atomicity covers database mutations using the supplied connection. Existing Document/User file unlinking, arbitrary plugin external effects or separate connections, and a plugin that takes over/commits the writer transaction cannot be reversed by DB rollback. The guard rejects changed transaction nesting rather than silently committing the wrong savepoint. No DDL, foreign-key weakening, migration version or ledger change is introduced by this batch.

Validation uses exclusive `itsm_port_purge_review` provider databases cloned consistently from the completed disposable canonical checkpoint. PostgreSQL used a quiescent database template; MariaDB used a native consistent dump. This is populated application validation, not a new fresh-install or migration-replay claim. Fresh canonical installation and full history are validated separately by the main workstream. The focused tests cover real autocommit and caller savepoints, invalid/stale/self/discriminator-independent public identities, hooks cancelling/throwing before and after cleanup, related update refusal, public typed consumable/computer/user replacements, root/tree/global scopes, soft delete, actual queued transport timing, and actual HTTP scoped User decisions and extension behavior. The HTTP fixture runs only through a private token-protected localhost subprocess router under tests; no production route is added.
