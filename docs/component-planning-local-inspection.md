# Component planning uses one local table inspection

The Motherboard, Memory and HardDrive adoption plans previously inspected the same component table in the payload planner, read its columns again in the staged planner, and inspected it again in the typed relationship planner. Each public component plan now captures one DBAL `Table` from its supplied connection and passes it through those three read-only planning steps. The typed planner clones the borrowed table before removing DBAL-synthesized indexes.

The existing public `plan()` signatures remain unchanged. The internal typed/staged extension accepts only an exact frozen target table name; the payload helper likewise checks its frozen snapshot table before acquiring metadata or reading the ledger. A DBAL table carries no connection ownership capability: the concrete public caller remains responsible for obtaining it from the supplied connection. The helper is not a cross-call cache.

For each pending component public plan, source call counts change from two full introspections to one, three column inspections to one, three index inspections to two, and two outgoing-FK/options inspections to one each. The separate physical-index read remains necessary because DBAL can synthesize supporting indexes that PostgreSQL never created. Incoming owners, composite reference ordering, native generated-column inspection, invalid-data audits and all frozen SQL producers remain unchanged. Apply still invokes a new public plan after each DDL phase; callbacks, reconstruction and retry never reuse this inspection.

The new nonconnecting ownership contract rejects unrelated, case-different and namespace-different table snapshots before any connection acquisition and retains public signatures. It adds one discoverable contract by source filename; actual discovery and execution are pending. Original component/processor contracts, frozen migration definitions, historical SQL, ledger state and phase behavior are unchanged. Syntax/style, pure execution, native plan equivalence, populated retry, both-provider full suites and final schemas remain ROOT validation gates.

The earlier MariaDB component diagnostic timed out at its unchanged 300-second limit. This source consolidation does not establish that timeout's cause or a speed improvement. ROOT then compared the global incoming-projection query with eight per-target queries in three read-only runs on the retained catalogue: global reads took 1.463/1.381/1.344 seconds, while each eight-query total took approximately 11.043 seconds. Complete projected rows agreed and ledger/native DDL remained unchanged. That rejects the separately prepared `f05` per-target strategy for this workload. This candidate is based directly on the earlier `bfc99` source and retains its one call-local global inventory. The earlier candidate and its source review remain evidence, not an accepted runtime optimization. No visible owner or historical table is hidden or dropped.
