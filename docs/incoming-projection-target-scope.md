# MySQL incoming projection target scope

IncomingProjectionReferences::has() now limits its MySQL/MariaDB KCU read to the requested referenced schema, referenced table and items_id column. A consumer in another database remains visible because no referencing-schema/table restriction is added. Each planning object captures both positive and negative results separately for the exact target identity; it does not treat the first target read as a complete global inventory. Literal schema/table punctuation remains bound, and returned native spellings must equal the requested names so catalogue collation cannot merge distinct targets.

The existing constructor retains the supplied DBAL connection and its visibility/permissions. A failed catalogue query still propagates before destructive migration planning can continue. The reader writes no schema, data, receipt or configuration. This is migration infrastructure, not a domain-query conversion or a new relationship registry. PostgreSQL's existing native relation/attribute-ID inventory is unchanged.

Actual callers are the owning projection guards in TypedItemMigration::plan(), SoftwareTypedItemMigration20261011::plan() and ProcessorTypedItemMigration20261012::plan(). They request the actual source table/schema before replacing a legacy or generated projection. LegacyToOrm::plan() supplies one planning context to its frozen typed stages. Standalone stages create their own context when needed; staged application replans after DDL rather than retaining this object's capture across phases. No caller signature, optional context forwarding, frozen target declaration, historical DDL or migration version changes.

mysqlSnapshots()/mysqlReferences() are byte-unchanged. Their preservation role requires every composite ordinal and action, grouped by actual referencing schema/table/constraint. They are not replaced by the existence query. The complete native incoming-projection contract, processor composite-reference control and component composite incoming-FK fixture retain their original assertions. A projection in a composite FK's second ordinal remains a hard adoption refusal, even for an external custom consumer.

The source unit contract retains the original reference-presence/schema/fresh-context cases and adds MariaDB, exact bound-query ownership, repeated positive and negative captures, literal punctuation, and collation-lookalike controls. Its old one-global-read expectation is intentionally replaced on MySQL by one read per distinct requested target per planning object. PostgreSQL keeps the original single inventory read. In the controlled original scenario this means five MySQL target reads in the first context and eight total across later contexts, rather than one then three global reads. These are source test expectations, not runtime measurements.

No LIMIT1 is applied before native spelling validation: a case-insensitive catalogue predicate may return a lookalike target before the exact target. The reader must examine the bounded target matches to retain the prior native identity semantics. It does not fetch unrelated targets or hide any visible catalogue. A LIMIT1 optimization would require separate proof of exact native identity selection and pushdown; it is not part of this change.

The prior source audit identified the global KCU read as one opportunity under the retained visible historical catalogue. This candidate makes that scope explicit but does not claim the component contract's delay or any timeout cause is resolved. DBAL's independent RC join, repeated target introspection and required phase replans are unchanged. No installed-vendor patch or cross-DDL/global cache is introduced.
