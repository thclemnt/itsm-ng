# Session authorization fixture and dynamic grant ownership

Actual password login applies the local authorization rules through public User update. Rule-owned (`is_dynamic`) profile grants absent from the current rule output are removed. A grant intended to survive that lifecycle must be manual.

On cleanab424 the original Session authorization contract failed its strict preferred-profile/child-scope assertion on both PostgreSQL and MariaDB. Root-owned bounded native diagnostics preserved the assertion and observed nine grants becoming six: the first profile's static nonrecursive parent grant survived, its dynamic recursive duplicate was removed, and login selected the parent scope instead of the preferred child. Preferred/default/active identifiers were correctly typed integers. This is a fixture ownership error, not evidence for changing identifier types or bypassing authorization rules. Before evidence: `session-authorization-ab424-selection-pg.json` and `session-authorization-ab424-selection-mysql.json` in the cloud evidence directory. Diagnostics completed with the original assertion failure still recorded and supplied writer/idleness/ledger/source/config preserved.

The fixture keeps the same first-parent duplicate order but makes the nonrecursive duplicate dynamic and the recursive grant manual. Before login, duplicate merging, supplied-connection revocation and rollback still exercise the captured recursive grant. After actual login, a fresh owning ProfileUser lookup checks that the dynamic duplicate has been retired and the complete manual recursive grant retains its user/profile/entity ownership and Boolean flags. The original strict preferred selection assertion, permission masks, hooks, API refusals, recursive scopes, token admission and rollback assertions remain intact. No Auth/User/Session production code, rights-rule policy, cache invalidation, fixture refill or expected-value casts change.
