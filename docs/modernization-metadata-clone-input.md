# Canonical clone input boundary

The actual PostgreSQL e658 software allocation ownership contract failed at its first positive clone. CommonDBTM copied the source canonical `monitors_id`, then replaced only the caller's partial `itemtype/items_id`; entity input conversion correctly refused their disagreement. This is a production clone preparation defect, not a reason to relax the allocation assertion.

CloneInput now normalizes each supplied discriminated override through the mapped entity's LegacyInput policy before merging it with the source. Only the current discriminator/logical identity supplies context; old owning columns do not enter the proposal. Entity-generated compatibility columns are omitted from the copied writes, then their logical values are rederived from the final canonical selection for existing public authorization and add hooks. User::prepareInputForAdd, for example, requires the correct derived auths_id to avoid supplying its zero default. Both supplied canonical NULLs and entity-defined empty/fallback policies remain authoritative. Scalar overrides retain array-key semantics: an absent key copies the source; a supplied NULL stays NULL.

EntityRegistry's generated-column/fallback-column views come solely from Doctrine field flags and the entity property DiscriminatorKey. There is no clone relationship registry, table switch or field-name heuristic. Unmapped plugin models retain their existing merge behavior. Four relation-specific clone overrides in Appliance_Item, Appliance_Item_Relation, Item_OperatingSystem and Item_Project only repeated this preparation; they now inherit the shared boundary. Their add/update authorization, lifecycle hooks, notifications, audit, concrete model classes and relation selection remain in their existing public paths.

The Clonable trait already normalizes concrete relation withReference proposals before clone; its body remains unchanged. Deprecated copy helpers also pass complete retargeted data through normal public add. CommonDBTM still invokes prepareInputForClone and public add, then post_clone in its previous order. The wider defect where a parent clone or post_clone child failure may leave a partially created graph remains OPEN; this change does not promise whole-graph atomic cloning or change notification routing.

The existing software-allocation-ownership positive/negative clone assertions remain byte-for-byte unchanged. typed-parent-cloning adds real direct Document_Item legacy/canonical/scalar clone commands, native owning/projection vectors, rejected disagreement/required NULL and no-insertion controls; real Computer clones distinguish explicit scalar NULL from absent overrides. Additional real entity-policy controls cover numeric authentication fallback and optional processor stock NULL kind. Every previous typed-parent assertion, setup operation and cleanup remains unchanged, and all frozen migrations/Baseline/ORM declaration bytes are preserved.

SOURCE-only checkpoint: no PHP/compiler/style/bootstrap/native/browser/CI run by the source author. ROOT must compile, run focused software-allocation-ownership and typed-parent-cloning plus existing appliance/project/operating-system cloning contracts on both providers, inspect schema/foreign keys and run coherent full suites before accepting runtime behavior. Current e658 installation and old operational packets remain frozen; later integration needs a new exact source/runtime binding.
