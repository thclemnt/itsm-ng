# CI populated upgrade and original key ownership

The retained MySQL 8.4 and MariaDB 11.8 migration jobs from run 37222432607 fail with the original-encryption-key diagnostic. Their workflow imports `tests/migrations/schema.sql` and calls the current updater using `tests/migrations` as its configuration. That import creates no original encryption key. The release workflow has the same invocation boundary, even though its earlier independent installations have keys in other configurations.

The retained SQL fixture declares version GLPI 9.1.1 and 245 tables. The immutable supported adoption baseline declares 355 tables, including a notification-chat table absent from that older dump. The CLI checks for the key before invoking the upgrade coordinator's structural prerequisite check, so the observed missing-key failure does not establish that this historical dump is a supported current upgrade input. Copying an unrelated key or generating one next to the old dump would hide one failure and would not establish preservation of encrypted data or a supported historical upgrade chain.

This source candidate makes both workflow paths invoke the existing populated `migration-history.php` contract against a separate, freshly provisioned history database. A normal public CLI installation creates an independent disposable parent and its original key first. The contract constructs the immutable supported baseline and seeds, adds legitimate populated owner graphs, then copies that existing key into its private child configuration before invoking the real CLI preview/apply. It retains invalid-data refusal, raw-ledger adoption, identifier convergence, interruption/retry and final schema assertions. The child process budget stays 300 seconds.

Additional contract controls retain the original parent and child key digests across every preview/apply/refusal and preserve an actual encrypted configuration value through adoption. Neither the key bytes nor ciphertext is printed by these controls. The accepted value must remain decryptable with the original key after upgrade. No product security requirement, installer, migration definition or old SQL fixture changes. A lost key from a real existing installation still requires restoration; this candidate adds no regeneration fallback.
