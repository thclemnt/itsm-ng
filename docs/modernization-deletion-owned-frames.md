# Deletion transaction authority

DeletionUnit now uses the existing supplied DBAL owner's OwnedMutationFrame and ManagedTransactionScope. Returning to the same transaction nesting level cannot establish that a hook's original frame still exists: public commit/rollback followed by BEGIN, or close/reconnect, invalidates its capability. A stale parent also cannot start another deletion unit. Balanced deeper owned layers retain the parent capability; its terminal action still requires the exact original frame depth. No SQL keyword tracker, native driver calls or second connection owner is introduced.

Nested cancellation remains contagious even when a parent callback ignores the child result. Only a proven rollback of the actual original frame restores participating child models through LifecycleModelJournal, preserving absent properties and supplied null values. The optional third run argument restores the caller's parent model/session checkpoint exactly once after that rollback. Callback, owner, notification-barrier and restoration failures remain separately inspectable, preserving the earliest actual failure. A required-child DeletionCancelled object is normalized to a cancelled result only after cleanup stays clean; if restoration or notification cleanup fails, that actual first cancellation remains the inspectable primary. Scope loss permits neither rollback of a replacement transaction nor model rewind. Released savepoints still defer delivery to the caller's physical transaction; post-commit errors cannot authorize a rewind.

The CommonDBTM delete callsite must pass its existing restore closure as the third argument and remove unconditional catch/cancel restoration. That coordinated dependency is authored separately. DeletionUnit takes the supplied Connection and establishes that owner's frame; callers holding an adapter must additionally reject an adapter/connection substitution before accepting hook work. This change does not add actor ACL checks or alter purge semantics. Web, API, trusted rule/transfer and internal callers retain their actual authorization boundaries.

The new deletion-owned-frames contract uses real public Supplier child updates and post-update hooks, complete native supplier/history/queue vectors, absent/null checkpoints, child veto, nested cancellation, first failure plus independently failing restoration, caller-owned savepoints, balanced deeper layers, and actual public COMMIT/ROLLBACK/CLOSE followed by reconnect/replacement. Its continuity controls perform no application DML and require the replacement frame to survive refused cleanup. Only the fixture retires the replacement scope it captured. Existing purge/hook contracts, canonical history, mappings and installation producers are unchanged. Raw SQL/native commit followed by raw BEGIN bypassing the owner remains explicitly unsupported; this does not claim to retrospectively undo committed data.

SOURCE-only work is not native validation. ROOT must lint and run this new dynamically discovered contract and existing deletion/relationship/component/application portability controls on PostgreSQL and MariaDB, inspect schema and migration state, and run the coherent full suite. The application modernization goal remains open.
