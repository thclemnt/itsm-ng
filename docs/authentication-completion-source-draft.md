## Problem and resulting ownership

A successful login previously passed every loaded User field to User::update. Its valid preference-edit policy converts explicitly submitted values equal to global defaults to inherited NULL. Ordinary authentication thus changed unrelated stored preference ownership; ROOT's original Maria API method passed while strict restoration correctly found highcontrast_css false becoming NULL. Token generation itself only submits token/date.

AuthenticationCompletion now owns one persisted account identity, login time and directory-deleted marker, plus an explicit AuthenticationRuleOutcome. User::completeAuthentication executes that outcome through the existing public update lifecycle, verifies actual stored completion and refuses if the account is no longer local with source0. Full stored model fields remain available as read/hook context; unrelated preferences are not update input. Ordinary deliberate preference edits retain the original default/inheritance policy.

## Executed rule intent

RuleRight records account assignments and dynamic grants at its actual existing action branches. Equal-valued assignments remain intentions, including timezone, active status and default entity/profile/group. There is no output-versus-row difference inference or additional action switch. Discarded/stop-import action groups retain original behavior. Normal rule matching, regex results, stop-on-first, plugin callbacks, escaping and legacy processAllRules output remain in the same evaluation.

RuleRightCollection binds an evaluation-owned collector through a protected process-one-rule seam whose default preserves normal dispatch. The Rule and Collection restore their previous typed context in finally, supporting nested evaluation without a global registry or request flag. Match-control metadata and dynamic grant transients retain their lifecycle meaning. Unknown rule implementations explicitly refuse the modern evaluation until they have an authoritative producer; there is no silent full-row fallback. Standard RuleRight custom assign targets still flow through the actual default assignment branch and normal User preparation/filter/authorization.

## Scope and remaining legacy routes

Verified local credential login owns completion and local-rule outcomes. API-token and cookie authentication use it only when the stored account is local/source0 and no actual external synchronization producer ran. A typed VerifiedLoginProvider records the actual credential producer independently of the stored account source. API/cookie completion projects the prior _extauth transient to public lifecycle hooks; local password completion does not. This context never classifies writable ownership. Actual LDAP retrieval clears the modern completion before invoking a possibly partial producer; SSO retrieval also clears it. LDAP/mail/SSO, nonlocal alternate-source accounts and new-account auto-add retain explicit legacy paths. Their full-row preference defect remains OPEN until mapped synchronization outcomes own their actual configured attributes, groups/emails/pictures and rules. A first local batch does not complete authentication modernization.

CommonDBTM and User still own input protection, actual endpoint authorization, default entity/profile/group checks, callbacks, audit, User email/group/right synchronization and manual-grant preservation. This batch adds no persistence SQL, static manager, schema or migration. Existing supplied-adapter read/write selection and slave handling remain; slave mode never runs completion or auto-adds. A refused required completion now refuses login rather than silently treating the attempted input as successful. Callback changes to unowned input are explicit callback intentions, not row-copy effects.

An explicitly executed is_active assignment is a required security-rule admission outcome. Typed per-operation User context checks it after normal preparation, after the final public pre_updateInDB callback and Boolean normalization, and in the actual persisted postcondition. A hook that drops or overrides this decision refuses completion rather than admitting an active account. Ordinary callback intentions remain permitted for other fields. The pending context is consumed by one public update; nested ordinary edits have their own policy, nested completions restore their own context, and outer lifecycle fields/input/updates/history view are restored finally around the entire nested completion, including its initial and final account reloads. A genuine late callback with an already prepared non-boolean rule write verifies exact persistence after nested completion. Actual completion reloads after callbacks so nested writes are not mistaken for an untouched row. Completion postconditions also check actual last_login and directory-deleted marker after hooks. This is not a new atomic auth transaction: earlier expiration maintenance, external files/notifications, hook-controlled transaction replacement/raw COMMIT, and multi-grant failure rollback are not solved. There is no claim of concurrent source-transition locking, live replica behavior or complete plugin compatibility. The broader managed writer/frame prerequisite must validate before a transaction ownership milestone.
